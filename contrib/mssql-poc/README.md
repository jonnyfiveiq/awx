# AAP Controller on MS SQL Server - POC Guide

**ANSTRAT-1887: Bring Your Own Database (BYOD) - MS SQL Server**

This guide walks through running AAP Controller (AWX) with ALL ORM traffic on Microsoft SQL Server, retaining PostgreSQL only for `pg_notify` (used by dispatcherd for real-time event dispatch).

## Architecture

```
                    ┌─────────────────────────────┐
                    │    AAP Controller Pods       │
                    │  (controller-task / web)     │
                    ├─────────────────────────────┤
                    │  Django ORM (all models)     │
                    │         │                    │
                    │    MSSQLRouter               │
                    │    ┌────┴────┐               │
                    │    ▼         ▼               │
                    │  mssql    default            │
                    │  (R/W)   (pg_notify only)    │
                    └────┬─────────┬──────────────┘
                         │         │
                    ┌────▼────┐ ┌──▼──────────┐
                    │ SQL     │ │ PostgreSQL  │
                    │ Server  │ │ (pg_notify) │
                    └─────────┘ └─────────────┘
```

## Prerequisites

- **Kind cluster** with AAP 2.7 deployed (controller-task and controller-web pods running)
- **MS SQL Server** accessible from the cluster (Azure SQL Edge for ARM64/Apple Silicon, or SQL Server 2019+ for x86)
- **kubectl** configured for your cluster
- **Container build access** to add ODBC drivers to controller images

## Step 1: Add MSSQL Dependencies to Controller Image

Add the ODBC driver and Python packages to your controller container build. Use the provided `Dockerfile.fragment`:

```dockerfile
USER 0

RUN curl -s https://packages.microsoft.com/config/rhel/9.0/prod.repo > /etc/yum.repos.d/mssql-release.repo && \
    microdnf install -y unixODBC unixODBC-devel && \
    ACCEPT_EULA=Y microdnf install -y msodbcsql18 && \
    microdnf clean all

RUN /var/lib/awx/venv/awx/bin/pip install --no-deps mssql-django==1.7.3 pyodbc==5.0.1
```

If using Skaffold/fragments, place this as a numbered fragment (e.g. `03-install-mssql-deps`) in your container build fragments directory. Rebuild and deploy the controller images.

## Step 2: Create Schema on SQL Server

Run Django migrations against the `mssql` database. This requires a temporary configuration that allows migrations on `mssql`.

First, deploy a minimal version of `mssql-confd.py` (without the router's `allow_migrate` block returning `False`) so that migrations can target SQL Server. Then run:

```bash
kubectl exec -n <namespace> <controller-task-pod> -c <container> -- bash -c "
  source /var/lib/awx/venv/awx/bin/activate
  awx-manage migrate --database=mssql
"
```

Some migrations may fail on SQL Server. Fake them:

```bash
# Partitioning not available on SQL Server
awx-manage migrate main 0144 --database=mssql --fake

# These may fail due to SQL Server syntax differences
awx-manage migrate main 0069 --database=mssql --fake
awx-manage migrate main 0185 --database=mssql --fake
awx-manage migrate main 0187 --database=mssql --fake
awx-manage migrate main 0189 --database=mssql --fake
```

After faking, re-run `migrate --database=mssql` until all migrations pass.

## Step 4: Deploy the MSSQL Configuration

Deploy `mssql-confd.py` as `/etc/tower/conf.d/mssql.py` on the controller pods. In a Kubernetes deployment, add it to the `myaap-controller-app-credentials` Secret under the `mssql.py` key:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: myaap-controller-app-credentials
type: Opaque
stringData:
  mssql.py: |
    # Paste contents of mssql-confd.py here
    # Adjust HOST, PASSWORD, PORT as needed
```

The configuration file (`mssql-confd.py`) does the following:

| Component | Purpose |
|-----------|---------|
| `DATABASES['mssql']` | SQL Server connection using `mssql-django` backend |
| `MSSQLRouter` | Routes ALL ORM reads/writes to `mssql`; blocks migrations on `mssql` |
| `SET XACT_ABORT OFF` | Allows savepoints to work correctly on SQL Server |
| `_MSSQLAtomicWrapper` | Patches `transaction.atomic()` to default to `mssql` instead of `default` |
| `_mssql_on_commit` | Patches `on_commit` callbacks to default to `mssql` |
| `_mssql_advisory_lock_noop` | No-op for PostgreSQL advisory locks (not available on SQL Server) |
| `_mssql_bulk_create` | Row-by-row fallback for `bulk_create(ignore_conflicts=True)` |
| `_mssql_patched_update_host_metrics` | Raw SQL replacement for HostMetric upsert (avoids Django transaction state issues) |

### Important: `weak=False` on Signal Handlers

All `connection_created.connect()` calls use `weak=False`. This is critical because conf.d files are loaded via `exec()` and without strong references, Python garbage-collects the handler functions when the exec scope exits, silently disconnecting them.

## Step 5: Register Execution Environments

After the router is active, register the default execution environments on SQL Server:

```bash
kubectl exec -n <namespace> <controller-task-pod> -c <container> -- bash -c "
  source /var/lib/awx/venv/awx/bin/activate
  awx-manage register_default_execution_environments
"
```

## Step 6: Migrate Reference Data (Optional)

If you need data that was previously created on PostgreSQL (RBAC roles, settings, etc.), run the migration script inside the controller-task pod:

```bash
# Copy script to pod
kubectl cp scripts/migrate_pg_to_mssql.py <namespace>/<pod>:/tmp/migrate_pg_to_mssql.py -c <container>

# Run migration
kubectl exec -n <namespace> <pod> -c <container> -- bash -c "
  source /var/lib/awx/venv/awx/bin/activate
  python /tmp/migrate_pg_to_mssql.py
"
```

The script reads from PostgreSQL (`.using('default')`) and writes to SQL Server (`.using('mssql')`), handling `IDENTITY_INSERT` and skipping existing rows.

## Known Limitations

- **pg_notify**: PostgreSQL is still required for dispatcherd's `pg_notify` real-time event dispatch. This is a raw `psycopg` connection, not ORM.
- **Partitioning**: SQL Server does not support PostgreSQL-style table partitioning. Migration 0144 is faked; event tables are unpartitioned.
- **Resource registry**: `dab_resource_registry_resource` migration has a UUID column size mismatch. Non-critical, skipped.
- **periodic_resource_sync**: Fails with 401 to Gateway. Pre-existing issue, unrelated to SQL Server.
- **mssql-django maintenance**: The `mssql-django` package (1.7.3) is community-maintained. Production use would require evaluation of long-term support.

## Monkey-Patch Rationale

AWX assumes PostgreSQL throughout. Rather than modifying AWX source code, this POC uses runtime monkey-patches loaded via Django's `conf.d` settings mechanism. This approach:

1. **Zero AWX source changes** - the fork is identical to upstream
2. **Fully reversible** - remove `mssql.py` from conf.d to revert to PostgreSQL-only
3. **Isolates SQL Server concerns** - all MSSQL-specific logic lives in one configuration file

The patches address these PostgreSQL-specific assumptions:
- `transaction.atomic()` defaults to `'default'` (PostgreSQL) - patched to default to `'mssql'`
- `advisory_lock` uses PostgreSQL advisory locks - replaced with no-op
- `bulk_create(ignore_conflicts=True)` generates PostgreSQL `ON CONFLICT DO NOTHING` - replaced with row-by-row insert
- `_update_host_metrics` uses Django ORM upsert pattern that breaks SQL Server transaction state - replaced with raw SQL `IF NOT EXISTS/INSERT` + `UPDATE`
